### Where this plan departs from `caj-readiness.md` Block 6

1. **Output**: that plan keeps the head of one combined log (16 MiB cap, then a
   marker). Here stdout and stderr are separate streams that keep the **tail**
   (current + one previous file, 8 MiB rotation), with absolute offsets.
2. **Status**: that plan has `execinfo` plus an in-memory ring of 128. Here
   `exec-status` reads a small per-exec state file in addition to the live
   table, so a finished exec stays answerable (until retention) and survives a
   supervisor restart. The ring is dropped.
3. **Authorization**: that plan adds one `Op::ExecInfo` open to all roles. Here
   an observer may read status only, a member may read output and signal only
   its own seat's execs; this needs three ops plus an ownership check inside the
   single `authorize` function (see 3.4).
4. **Revision gate**: that plan refuses client-side with exit 2. Here a new
   command against a revision-3 session exits **125** with a `hisn-error/v1`
   object, code `E_UNSUPPORTED` (task text).
5. **Limit 32 concurrent**: kept (each detached exec costs one waiter thread and
   two pump threads).

## 2. Data model

### 2.1 Incarnation
`Shared.incarnation: String`, created once at supervisor start:
`<UTC compact YYYYMMDDTHHMMSSZ>-<4 hex from getrandom>`, e.g.
`20261122T101500Z-9f3a`. Safe in a file name. Reported in `ls --json`
(`incarnation` at top level) and in `session.json` is **not** changed. A
detached exec is identified by `(incarnation, exec_id)`.

### 2.2 Files (all in `<workspace-dir>/exec/`, dir 0700, files 0600)
```
<incarnation>-e<N>.state.json     status record (atomic write: temp + rename)
<incarnation>-e<N>.stdout         current stdout file
<incarnation>-e<N>.stdout.1       previous stdout file (after first rotation)
<incarnation>-e<N>.stderr         current stderr file
<incarnation>-e<N>.stderr.1       previous stderr file
```
State file `hisn-exec-state/v1`: `{incarnation, exec_id, seat (string|null),
argv0, started (RFC3339), ended?, state: running|exited|signalled, exit_code?,
signal?, signal_name?, cause?: exit|signal|exec-signal|session-stop, pid,
stdout: {total, base}, stderr: {total, base}}`. `total` = bytes written over the
stream's life; `base` = absolute offset of the first byte of the **previous**
file if present else of the current file (the oldest available offset).
Written at start, at each rotation, and at end. A supervisor crash leaves
`state: running` with a dead pid; `exec-status` then reports `state: "lost"`
only when the incarnation differs from the live one (documented).

### 2.3 Output pump (per stream)
A supervisor thread reads the pipe read end and appends to `<stream>`;
when the current file reaches 8 MiB (`EXEC_ROTATE_BYTES`) it renames
`<stream>` over `<stream>.1` and opens a new `<stream>`. State (`total`, base of
current `cur_base`, base of previous `prev_base`) lives in an `Arc<Mutex<..>>`
shared with readers. At most 16 MiB per stream is kept. A rotation may split a
UTF-8 character or line; offsets are bytes.

### 2.4 Read semantics (`execoutput`)
Request `offset` (default 0), `max` (default and cap 1 MiB). Reply
`{data_b64, offset (actual start), next, total, oldest, rotated_away: bool,
eof: bool}`. If `offset < oldest`, return from `oldest` with
`rotated_away: true`. `eof` = exec finished and `next == total`. The data is
read under the stream mutex so a rotation cannot interleave (a read that spans
`.1` and current is stitched). CLI `exec-output` writes raw bytes to stdout and
prints `next` offset on stderr (`next=<n>`), or the full object with `--json`.
After the exec has ended and the supervisor is alive, the same in-memory state
serves it; after a supervisor restart, status and output are read from the
files (state file + the two stream files) by the same code path with no live
pump.

### 2.5 Retention
Logs of finished execs follow the workspace journal retention: a finished
exec's files are deleted when its `ended` time is older than the oldest
`ts` still in the journal (`first_wseq_in_file` record), or when more than 256
finished execs are kept (oldest first). Pruning runs at supervisor start and
after each exec finishes, never touches a running exec, and never touches
a running exec of the live incarnation (a state file with `state: running`
and a different incarnation is treated as lost, hence prunable). Documented in
`docs/sessions.md`.

### 2.6 Protocol (revision 4)
`PROTOCOL_REVISION` 3 -> 4. New / changed requests (all `client` optional as
today):
- `exec` gains `detach: bool` (`#[serde(default)]`). The CLI **omits** the key
  unless `--detach`. `detach` conflicts with `tty` and `attach`; the supervisor
  rejects the combination (`E_BAD_REQUEST`). No fds are sent for a detached
  exec; the supervisor builds them (2.7).
  Reply: `{"ok":true,"pid","exec_id":"e-N","incarnation","detached":true}`
  and the connection is closed (the exec runs on).
- `execstatus {exec_id}` -> state object (2.2 fields, plus `pid` only while
  running).
- `execoutput {exec_id, stream: "stdout"|"stderr", offset, max}` -> 2.4.
- `execsignal {exec_id, signal}` with signal in `TERM|INT|KILL|HUP`.
  (New op rather than reusing `signal`, because `signal` takes pid and
  non-detached execs and has other authorization semantics.)
`exec_id` on the wire stays `e-N`.
Version rules: supervisor accepts revision 3 and 4 clients (`version_gate`
unchanged: rejects `declared > own`; `own` becomes 4). A new command needs
`session.json protocol_revision >= 4`; a revision-4 CLI against a lower session
prints a `hisn-error/v1` `E_UNSUPPORTED` object ("requires protocol revision 4,
session has 3") on stderr and exits 125, nothing sent. A new supervisor
rejects `detach` / new ops from a client that declares `protocol_version < 4`
with `E_UNSUPPORTED` as well. Existing commands from a revision-4 CLI: the
declared `protocol_version` in `client` stays the **session's** revision gate
as today (`seat_material` declares `PROTOCOL_VERSION` only when the session
is >= 3). To keep requests byte-identical, `PROTOCOL_VERSION` sent by the
CLI is the constant 4 only when it must be; see risk R1.

### 2.7 Spawn path for a detached exec (security boundary)
`do_exec` is split: `do_exec_common` does validate + spawn + registration + exit
journaling; the connected path passes client fds, the detached path passes
supervisor-built fds: stdin = `/dev/null` (opened `O_RDONLY|O_CLOEXEC`), stdout
and stderr = write ends of two `pipe2(O_CLOEXEC)`. The spawn call is the same
`self.exec.spawn(&spec, stdio, ..)` under the same `spawn_gate`: same helper,
Landlock domain, network policy, seat attribution (`exec_seats[pid]`). No other
spawn site is added; a unit test greps that `exec.spawn(` has exactly two call
sites (the helper's own tests excluded) and a test asserts the detached path
calls the shared function. After the reply the supervisor closes its write
ends; the read ends go to the pump threads.
A waiter thread owns `drive_from_with_flag(&sp.status, pending, -1,
Duration::ZERO, false)` semantics with **no** connection watch: a new function
`exec::wait_exit(status, pending) -> Outcome` blocks on the status socket only.
When it returns it removes the table entry, journals `exec/exit`, updates the
state file, and runs pruning. Kill via `execsignal` uses the existing `K <n>`
path.

### 2.8 Authorization (3 new ops, one function)
`Op::ExecStatus`, `Op::ExecOutput`, `Op::ExecSignal`.
`allows`: Owner all; Member: ExecStatus, ExecOutput, ExecSignal; Observer:
ExecStatus only. Ownership ("a member may signal only execs started by its own
seat") needs the target's seat, so `authorize` gains one more input,
`target: Option<&ExecTarget>` (`ExecTarget { seat: Option<String> }`), supplied by
the supervisor from the detached-exec registry before the call (unknown id ->
`None` -> the op runs and answers `E_NOT_FOUND`... after authorization; role
check first, so an observer asking for output of a nonexistent id is refused,
not told "not found"). In `authorize`, for `ExecSignal` with an
`Authenticated{role: Member}` the seat name must equal `target.seat`; owner
(uid, no credential) and Owner-role seats skip it. Refusals use the existing
`<op>/refused` journal path (`execstatus/refused`, `execoutput/refused`,
`execsignal/refused`), seat in `client`.
`ls --json` is `Op::List`-class (existing behaviour); it lists the detached
execs.

### 2.9 Journal records
- `exec/request` (detached): existing fields + `detach: true`.
- `exec/exit`: existing fields + `incarnation`, `exec_id`, `seat`
  (string|null), `pid`, `cause` in `exit | signal | exec-signal | session-stop`.
  `exec-signal` = an `execsignal` was delivered before the end and the exec
  ended by a signal; `signal` = ended by a signal nobody sent through hisn;
  `session-stop` = the stop flag was set when the status socket reported the end.
  For non-detached execs the new fields are **not** added (records stay as at
  v0.6.3, apart from `cause` staying absent) - compatibility.
- `execsignal/delivered` record (seat, signal, exec_id) so the cause is
  auditable.
- `session/stop`: new `detached_execs_ended: [{exec_id, incarnation, pid}]`,
  present only when non-empty.

### 2.10 Journal cursor index (Block 5)
Reader-side sidecar `journal.idx` per journal file (`journal.<n>.idx`,
`journal.idx` for the current file), mode 0600, JSON lines
`{"v":1,"file_len":L}` header then `{"wseq":W,"off":O}` every
`INDEX_EVERY = 1024` records. Rotated file names are never reused (existing
rule), so an index keyed by file name stays valid across rotation; the current
file's index is renamed together with the file in the existing rotation step,
and a missing one is rebuilt. Use:
1. `cursor_read` takes `first`/`last` wseq from `journal_info` style cheap
   head/tail reads (no full read), decides Reset / behind_retention.
2. Find the file whose range contains `after+1` (files are ordered; first wseq
   per file from the index header entries).
3. Seek to the greatest indexed `off` with `wseq <= after+1`, **verify** the line
   at that offset parses and has that wseq (inconsistent -> rebuild this
   file's index by one scan, then retry once, else fall back to the full
   scan of v0.6.3).
4. Read forward to the end of the journal (this and later files), so cost is
   O(records after the cursor + 1024).
The index is extended lazily by the reader (scan from the last entry to the
current end under no lock, atomic write temp + rename, errors ignored). It is
a cache: deleting it is always safe. Writers are untouched.

### 2.11 Unreadable lines (Block 5)
While reading forward, an unparseable or over-long line at byte offset `o` of
file `f` is not dropped silently. The reader remembers it; when the next
good record (wseq `b`) arrives with previous good wseq `a`, and `b > a+1`, it
emits a synthetic record: `kind: "journal/unreadable"`, `wseq: b-1`,
`ts` of record `b`, `session: ""`, `data: {file, offset, wseq_from: a+1,
wseq_to: b-1, count}` before record `b`. The cursor therefore moves past it and
contiguity holds. If `b == a+1` (the garbage line carried no wseq of its own, so
nothing is missing) nothing is emitted and it is only counted. An unreadable
tail at EOF with no later record is counted and not emitted. A gap in wseq not
covered by an unreadable line is still `E_CURSOR_GAP`, exit 4.
`journal --info` gains `unreadable` (count over files, from a scan cached in
the index header per file; rebuilt with the index) in `hisn-journal-info/v1`
(additive field).

## 5. Open risks

- R1: the `client.protocol_version` the CLI declares. Today it is
  `PROTOCOL_VERSION` (3) and only when the session is >= 3. If the constant
  becomes 4, every request from the new CLI differs byte-wise. Resolution: the
  CLI keeps declaring 3 for every existing command and declares 4 only on
  requests that use a new option/op. Byte-equality tests cover this.
- R2: `deny_unknown_fields` on a 0.6.3 supervisor makes `detach` fatal
  (`E_BAD_REQUEST`) even if the client check were skipped; the client-side
  revision gate is therefore the primary protection.
- R3: thread cost: 3 threads per detached exec x 32 against a scope's `TasksMax`.
  Limit stays 32.
- R4: a stopped session: pump threads must end when the pipes close; the stop
  path joins waiter threads with a 2 s bound. A grandchild that escaped the
  sandbox pid namespace cannot exist (pid ns teardown), but a hung join is
  bounded.
- R5: state file vs. live table drift on a crash: documented as `lost` only
  across incarnations.
- R6: the index is a cache read by an unprivileged same-uid reader; a forged
  index can only cause a verified fall-back to a full scan, never a wrong
  result (the offset line is verified, the run is contiguity-checked).
- R7: the unreadable-record synthetic `wseq` duplicates none: it uses the
  missing range's last wseq, and the next real record is `+1`. If two

## 8 Session A

Session A covers the detached-exec core in the order fixed by section 7 B6.

### 8.1 The three code questions

1. **Does the control-socket reader accept an exec request with zero fds?**
   Yes. `FdLineReader::next_line` (`src/control.rs` 461-498) returns
   `ReadLine { line, fds }` with `fds` empty when nothing arrived. In
   `serve_conn` (574-652) the `misuse` test (627-628) rejects only
   descriptors that arrive on a non-first or non-exec line, and an exec that
   is not first or is pipelined. Zero fds on a first `exec` pass. The
   rejection happens later, in `exec::validate` (`src/exec.rs` 116-127),
   which demands `fds == 3` (or 1 with tty), returning `Invalid::Fds`.
   `Supervisor::do_exec` (`src/supervisor.rs` 1291-1448) passes
   `stdio.len()` to it. Consequence: no change to `FdLineReader` or
   `serve_conn`. The detached path in `do_exec` builds the three fds
   (`/dev/null` + two pipe write ends) **before** `validate` and passes
   `stdio.len() == 3`. A `detach: true` request that *does* carry fds is
   refused with `E_BAD_REQUEST` (the supervisor does not adopt client fds for
   a detached exec). `detach` with `tty` or `attach` is refused too.
   After the reply, `serve_conn` loops to read another line; the CLI closes
   the connection, so nothing in `serve_conn` changes. The connection counts
   as a client only until the CLI closes it.

2. **Do the `ls --json` consumers tolerate new fields?** Yes.
   - The CLI does not parse `execs[]` into a struct. `live_session_view_pid`
     (`src/main.rs` 677-689) copies `r["execs"]` as `Vec<Value>`, and
     `session_v2_json` (708-781) puts it into the output unchanged.
     Top-level keys are added by `o.insert("supervisor_pid", ..)` (613-615).
     `incarnation` is added the same way, which needs the `sessioninfo`
     reply to carry it and `live_session_view_pid` to pass it on.
   - No schema file exists for `ls`: `schemas/` holds only
     `hisn-policy.v1.json`. The documented contract is prose: additive
     only (`docs/EXTERNAL-CALLERS.md` 36, `README.md` 57/246,
     `docs/sessions.md` 388).
   - The in-repo comparators (`tests/leak/l8.py`, `test_l8.py`) read with
     `json.loads` and pick fields by name.
   - `deny_unknown_fields` applies to requests (`control.rs` 69, 236) and
     `ExecSpec`, not to any `ls` or `sessioninfo` reply.

3. **Can `journal_files()` pick up the new files?** No.
   `journal_files` (`src/journal.rs` 1003-1022) lists only the workspace dir
   itself (`fs::read_dir`, not recursive) and keeps names matching
   `journal.<digits>.jsonl`, plus `journal.jsonl`. `rotate` (969-981) uses the
   same pattern. The exec files are in the subdirectory `exec/` and are named
   `<incarnation>-e<N>.*`, so they match neither. The session-B index name
   `journal.idx.<ino>` has no `.jsonl` suffix and does not match.
   **No change to the naming in the plan.**
