## 2. Design decisions

- **D1 (prune under live pump).** The `running` guard already protects a live-incarnation
  running exec. The hole is the *finished*-state exec whose pumps are still draining:
  `detached_wait` calls `prune_exec_logs` at supervisor.rs:1899, after removing the
  registry entry (1898) but BEFORE the drain loop (1905-1908) and the final state
  write (1909, which flips `output_open` to false via `refresh` at execlog.rs:752-757).
  Fix (Mashūra B1/B2, all three panel members):
  - In `execlog::prune`, a candidate is skipped when its writer may still be alive:
    `st.incarnation == live_incarnation || writer_gone(&st) != Some(true)`, AND
    `st.output_open == true`. A gone writer (foreign incarnation, `writer_gone ==
    Some(true)`) means dead pumps, so the files are prunable — crashed-supervisor
    files are still collected (existing tests `prune_leaves_running_state_of_live_foreign_pid`
    cases 2-3 keep passing).
  - Skipped candidates are removed from the `finished` vector entirely, so they do
    not count against `max_finished` (no extra deletions to compensate).
  - Move the `prune_exec_logs()` call in `detached_wait` to AFTER the drain loop
    and final `update()` (1909), so prune sees `output_open: false` for this exec
    and never races a pump that has already hit EOF.
  - Accepted trade-off: a grandchild holding a pipe open indefinitely keeps
    `output_open: true` and the files are retained (bounded by the session's life;
    the pumps end when the sandbox is gone, per code comment 1900-1904). No cap
    override in this release; noted as a known retention bound.
  Tests: `prune_skips_finished_with_output_open_and_live_incarnation` (skipped,
  not counted against the cap); `prune_collects_finished_with_output_open_and_gone_writer`
  (collected); existing prune tests unchanged and green.
- **D2 (detach in journal).** Add `detach: true` to the `exec/request` journal data
  for detached execs only (supervisor.rs journal write for the detached path).
  Non-detached records unchanged (compat). The wire `detach` field already exists
  (F4); no wire change, no revision bump.
- **D3 (E_TOO_LARGE).** Two sides, both additive (Mashūra B5):
  (a) Supervisor: discriminate oversize in `FdLineReader::next_line` with a typed
  signal (dedicated `ErrorKind`/variant, not string matching — non-UTF-8 and
  truncated-ancillary keep today's silent close). On oversize, `serve_conn` writes
  a wire reply `control::err(E_TOO_LARGE, msg)` (shape `{"ok":false,"error":…,
  "message":…}`, control.rs:454-456) naming the limit (65536) and "at least N"
  buffered bytes — the reader stops mid-stream, so the true size is unknowable
  without draining (DoS surface, rejected); then closes. Received fds are dropped
  by `ReadLine` ownership, never dispatched. Delivery is best-effort: a client
  still blocked in `write` may take EPIPE instead of reading the reply; documented
  as such. (b) Client: `execcli` checks its own request line length before
  `send_with_fds`, excluding the trailing `\n` (`MAX_LINE` excludes it;
  `line.len() > MAX_LINE + 1` with the newline formatted in) so an exactly-at-limit
  request passes; on exceed it prints the `hisn-error/v1` CLI object on stderr
  (the existing unconditional convention, execcli.rs:254-256) and exits 125
  WITHOUT sending. No new protocol revision (the reply shape exists).
  Adding `E_TOO_LARGE` to control.rs requires, in the SAME commit (Block 2):
  `docs/CONTROL-PROTOCOL.md` error table entry + `E_TOO_LARGE` in the
  `documented_error_codes_match_the_real_constants` `real` array (control.rs:2001-2015).
  Tests: unit `oversized_request_line_gets_too_large_reply` (exactly at limit passes,
  one over is refused with `err(E_TOO_LARGE, …)`; over the socket via `serve_conn`
  so the reply path is exercised, plus a raw-socket case since the client pre-check
  means leak tests never reach the supervisor path); client-side length check unit
  test (exactly-at passes, one-over exits 125 with the error object);
  leak case: `exec` with argv that pushes the line over 64 KiB → exit 125, stderr
  names the limit.
- **D4 (stdin passthrough, Block 3).** Today `--no-tty` sends `/dev/null` (F8) by
  design (help text, `refuse_stdin_token_unless_no_tty` rationale, terminal-acceptance
  test). Mashūra B3: making passthrough the default inverts a documented 0.6.3
  property and breaks shell loops / terminal-on-fd-0 callers. Decision: **opt-in via
  `--stdin-limit` presence**. Without the flag, `--no-tty` keeps `/dev/null` and the
  request is byte-identical to 0.6.4 (compat preserved). With `--stdin-limit <bytes>`,
  stdin is passed through the existing exec path (the pipe write end replaces
  `/dev/null` in the same `send_with_fds` slot, execcli.rs:692-701).
  - CLI: `--stdin-limit <bytes>` — clap `requires = "no_tty"`, `conflicts_with_all =
    ["tty", "detach"]` (usage error with `--tty`/`--detach`/default mode; no silent
    ignore). Accepted range 1..=1 GiB (1073741824); values outside are a usage error.
    `--stdin-limit 0` is rejected (a zero cap is a usage error, not "no stdin").
    Default when the flag is present: 64 MiB (67108864) is the cap the relay enforces
    if the user passes the flag without a value? No — the flag takes a value; there
    is no valueless form. The 64 MiB default applies when the flag is ABSENT, but
    absence means no passthrough at all (opt-in). Restated: presence ⇒ passthrough
    with the given cap; absence ⇒ `/dev/null`. Default cap for the passthrough path
    is 64 MiB when the user passes `--stdin-limit` with no value via
    `default_missing_value` — pinned in tests.
  - When fd 0 is a tty, keep `/dev/null` even with `--stdin-limit` (the terminal-
    acceptance test `no_tty_accepts_terminals_on_every_descriptor` must stay green;
    a tty on fd 0 with an explicit limit is a usage error instead? No: refusing the
    exec outright is more surprising than the documented `/dev/null` behaviour.
    Decision: tty on fd 0 + `--stdin-limit` ⇒ the relay is not started, stdin is
    `/dev/null`, and a `hisn:` warning on stderr says stdin was not passed because
    fd 0 is a terminal. Pinned by test.)
  - Relay thread (Mashūra B4): `poll()` on fd 0 with a wakeup pipe (triggered when
    the existing `stop` atomic is set) + non-blocking `pipe_w`; never `O_NONBLOCK`
    on fd 0 (shared open file description). Reads cap+1 bytes total to distinguish
    exactly-at-cap (close normally, exit = program's code) from one-over (flag
    `cap_exceeded`, close `pipe_w`). `EPIPE` on `pipe_w` (program closed stdin
    early, e.g. `head -c`) is a normal end, not a cap hit. The thread is never
    joined blindly: on `stop` the wakeup pipe ends the poll and the thread exits.
  - Cap-hit side effect (documented, not hidden): the program receives a clean EOF
    after the cap bytes and may commit (`sh`, `psql`) before the client replaces
    the exit with 125 + `E_TOO_LARGE` naming the stdin limit on stderr. Spooling
    to memfd before exec would remove this but loses streaming and needs a temp
    file in the client (rejected: larger surface, no benefit for the stated goal).
    The program's exit code is replaced by 125 — never silently truncated as if
    the input had ended.
  - Race, exit-line vs cap-hit: cap-hit wins if the relay flags it before the
    client returns; if the exit line and the flag arrive together, the flag wins
    (125). The relay never blocks the exit path (poll + wakeup).
  - Journal (O1, Mashūra B2): `stdin_limit` is NOT added to the wire (deny_unknown_fields
    + rev 4 already in 0.6.4 ⇒ any new field breaks a 0.6.5 client → 0.6.4
    supervisor). The cap is client-enforced; the supervisor never sees stdin bytes
    and cannot journal the hit. The hit is visible to the caller (125 + stderr);
    the journal keeps the existing records. Optional `note`-op marker after a cap
    hit is best-effort (seat role may refuse) — left as an open point, not built.
  - `--seat-token-file -` (F9): `read_token_line` consumes the credential line from
    fd 0 before the relay starts; the cap counts only the remainder. The relay
    starts after `seat_material` (execcli.rs:655), so counting is clean.
  - Detached: stdin stays /dev/null (no change; `--detach` has no stdio, F9).
  - Exec that never reads stdin: 1 MiB of stdin to `true` completes without hanging
    (poll + wakeup + EPIPE). Test must exist.
  - Stale text: `refuse_stdin_token_unless_no_tty` message (execcli.rs:82-84) still
    says `--no-tty` sets stdin to `/dev/null` — update it to name the opt-in.
  - Tests (unit where possible, leak otherwise): small input echoes; exactly at cap
    passes; one byte over → 125 + E_TOO_LARGE; binary with NUL bytes round-trips;
    credential line + data (cap counts data only); stdin-ignoring command + 1 MiB
    stdin doesn't hang; `head -c` early-close is normal; detached exec stdin is
    /dev/null (explicit: data piped to `exec --detach` is not delivered);
    tty-on-fd-0 with `--stdin-limit` warns and uses /dev/null.
- **D5 (capabilities).** `hisn capabilities --json` runs `check::run_checks()`
  (no session needed, F10) and maps check items to the 11 feature names. Schema
  `hisn-capabilities/v1`: `version` (crate version), `protocol_revision` (4),
  `declared_protocol_version` (3), `features: [{name, available, reason?}]`.
  Feature→check mapping (to be pinned in code, not ad hoc):
  `network-none|host|open` from the net/landlock checks; `rootfs` from rootfs
  availability; `ssh-agent`, `services` from their checks; `journal-cursor`,
  `journal-unreadable`, `detached-exec`, `exec-stdin`, `seat-credential-stdin`
  are compile-time true (the binary has them) — `available: true` always, unless a
  check says otherwise (e.g. open mode needs Landlock ABI: `network-open` false
  with the check's reason when the kernel lacks it). Text output without `--json`:
  one line per feature `name: available|unavailable (reason)`. Names documented in
  EXTERNAL-CALLERS.md and pinned by a test with the exact list.
- **D6 (profile validate --json).** Add `--json` to `ProfileCommand::Validate`.
  Schema `hisn-profile-validation/v1` with `"schema": "hisn-profile-validation/v1"`
  key. Shape: `{schema, ok: bool, errors: [{path, line?, column?, code, message}],
  warnings: [...]}`. Lines/columns are 1-based; JSON goes to stdout; fail-fast:
  `errors` has at most one entry today (anyhow returns the first error only) —
  documented. `warnings` has no producer today; the field is emitted as `[]` and
  the schema reserves it (open point: drop or keep — kept, as an empty list is
  forward-compatible and the task requires the field). Text output stays
  byte-identical: the text path keeps printing `resolved.to_toml()` on success and
  the anyhow chain on error exactly as today. The JSON path needs structured errors:
  introduce a `ProfileError` type (or extract from anyhow) carrying: TOML key path
  (dotted, e.g. `session.network`, `services[1].ready.socket` — `PolicyError`
  already produces these for policy validation; a toml byte span does NOT yield a
  dotted path, so path comes from the validation layer, line/col from the span),
  line/column (from `toml::de::Error::span()`, a byte range, computed against the
  source text — `toml 1.1.8` per Cargo.toml; confirm the exact API at
  implementation, fallback: no line/col), stable code (`E_PROFILE_PARSE` for all
  deserialization errors — toml exposes no structured enum distinguishing syntax /
  type / unknown-key, so string-matching serde messages is rejected as brittle;
  `E_PROFILE_VALUE` for validation failures with a known path). Where nothing is
  known, omit `path` (or `null`) rather than `""`. The refused profile in the
  session's cwd is a valid test input (it must produce errors, not a crash) —
  use a fixture file, not the live cwd (environment-dependent). Exit code: 0 if
  ok, 125 (EXIT_INTERNAL, main.rs:17-26) if not — confirmed at main.rs:17-26.
  Tests: unknown key, wrong type, invalid value, session-cwd refused profile
  (fixture), valid profile (ok:true, empty lists); golden test on the current
  error text before the `ProfileError` refactor so text output is pinned
  byte-identical.

## 5. Open risks / points

- **O1** Journal record of a stdin-cap *hit* (D4): the supervisor cannot see stdin
  bytes and no wire field is added (deny_unknown_fields + rev 4 in 0.6.4). The hit
  is visible to the caller (125 + stderr) but not in the journal. A best-effort
  `note` op after a hit was suggested by Mashūra; not built (seat role may refuse).
  Accepted as a documented limitation.
- **O2** `toml 1.1.8` span API for line/col in profile JSON (D6): confirm
  `TomlError::span()` shape at implementation. Fallback: path only, no line/col.
- **O3** RESOLVED by Mashūra B2: no wire field, no revision bump. compat_063.sh
  stays green by construction (no wire change in Block 3).
- **O4** RESOLVED by Mashūra B6: no `exec --json` flag. `E_TOO_LARGE` uses the
  existing unconditional `hisn-error/v1` CLI convention on stderr.
- **O5** The supervisor-side E_TOO_LARGE reply (D3a) changes a silent close into a
  reply for oversized lines — additive. Delivery to a still-writing client is
  best-effort (EPIPE possible); documented. compat_063.sh wire tests use small
  requests and are unaffected.
- **O6** Test machine disk: re-check free space before every heavy run; clean own
  build output below 3 GB.
- **O7** `capabilities` mapping: check-item names in check.rs must be read at
  implementation time and pinned in the test (D5 mapping table is provisional).
  Semantics per feature: `journal-cursor`, `journal-unreadable`, `detached-exec`,
  `exec-stdin`, `seat-credential-stdin` are binary facts (`available: true` when
  the code path exists — document that an older running supervisor may still
  refuse them); network/rootfs/ssh-agent/services are host-check-derived.
  Exit code is 0 whenever the report is produced (features may be false).
  `protocol_revision` is read from `sessionmeta::PROTOCOL_REVISION`, not a literal.
- **O8** compat_063 skip→fail (Mashūra O-C): on a machine where `unshare -Ur` is
  legitimately unavailable the gate goes red instead of green-with-3-checks. That
  is intended (the task requires it); the test machine is the arbiter.
- **O9** `capabilities` text format: `name: available` / `name: unavailable (reason)`;
  parentheses printed only when a reason exists. Pinned in the test.
