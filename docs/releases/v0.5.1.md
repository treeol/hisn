# hisn v0.5.1

0.5.1 gives the journal's "who" substance: named **seats** with a credential
and a role, per workspace. A seat created once is valid in every session of
its workspace, so a project is set up once and every later session is
distinguishable by seat in `hisn journal`.

## Known boundary — read first

Under one Unix user a seat is **attribution and a guard against mistakes,
not a security boundary**: any process of that user can omit the credential
(and be the owner) or read the user's files. A seat credential says "this
client is acting as seat X"; it does not stop a same-uid process from acting
as the owner. Real separation comes with separate Unix users, in a later
step. Every document that describes seats says this in plain words.

## What is new

### Seats

`hisn seat add|ls|set-role|revoke` with `--workspace NAME-or-ID` or
`--session ID-or-NAME` (else the current directory's workspace) writes the
workspace seat store `seats.json` in the workspace state directory (never
inside a session's view). A seat has a name, a role, a creation time, an
optional expiry and an optional revocation. The credential is a random
256-bit token, shown exactly once by `add`, stored only as its SHA-256 hash,
and compared in constant time. It is never written to the journal,
`grants.jsonl`, `session.json`, `ls` output, logs or error messages.

### Roles

The one role table, in `src/authz.rs` — every op is assigned, no op is
unassigned:

| op | owner | member | observer |
|---|---|---|---|
| grant, revoke, kill | yes | no | no |
| seat-add, seat-ls, seat-set-role, seat-revoke | yes | no | no |
| exec (incl. attach), signal, note | yes | yes | no |
| list, inspect, sessioninfo | yes | yes | yes |

A same-uid client that presents no credential is the owner, exactly as
before. A presented credential that is unknown, revoked or expired is
refused and never falls back to owner; the refusal names the seat, the op
and the required role, and is journaled. The owner may give a seat the role
`owner` (delegation). `seat set-role` and `seat revoke` take effect in
already running sessions of the workspace, without a restart.

### Command line

`hisn seat add NAME --role owner|member|observer [--expires TIMESTAMP]`
creates a seat and prints the credential once, with a note that it cannot
be shown again. `hisn seat ls` lists names and roles, never credentials.
Every command that talks to a session (`exec`, `attach`, `grant`, `revoke`,
`kill`, `stop`, `note`, `ls --session`, `inspect`) takes the credential
from `HISN_SEAT_TOKEN` or `--seat-token-file PATH`, never from a
command-line argument, and never into a session's environment. Five
examples exist on the wire too: `seat-add`, `seat-ls`, `seat-set-role`,
`seat-revoke`, plus the `seat_token` field of `client` (all at protocol
revision 3; see below).

### Journal and listings

When a credential was used, journal records carry the **server-set** seat
name and role (`JournalClient.seat`, `JournalClient.role`), with
`label_source` `"seat"`. The seat name is never the client's label: choose
`--client` as you like, `hisn journal --seat NAME` still selects the
server-set seat, and the old label match stays as the legacy behaviour for
records without a seat field. Seat management is journaled (who created,
changed or revoked which seat, never the credential). `ls --json` gains an
additive `seats` key per session (names and roles, never credentials);
`sessioninfo` does not carry it — seat names are not observer information.
`grants.jsonl` gets no new field: for a credentialed client the audit label
is the seat name.

### `session.json`

Unknown fields nested inside `owner`, `lease` and `members` now survive
rewrites just like the existing top-level ones.

## Protocol revision 3

`client.protocol_version` / `protocol_revision` is now `3`. The
`seat_token` field and the four seat ops exist only at revision 3. Against
a session below revision 3 the 0.5.1 CLI refuses with exit 2 and sends
nothing — exactly as `note` refuses below revision 2 — when a credential
is configured; a client without a credential behaves exactly as in 0.5.0.

## Setting up a seat in three commands

```sh
# 1. Create the seat once for the workspace. The credential is printed once.
hisn seat add member1 --role member
# 2. Use it. The token travels in the environment (or --seat-token-file).
HISN_SEAT_TOKEN=<token> hisn exec --session demo -- sh -c 'echo ok'
# 3. See what that seat did, and revoke it when it should stop.
hisn journal --session demo --seat member1
hisn seat revoke member1
```

## Compatibility

- A client that sends no seat credential behaves exactly as in 0.5.0: same
  requests, same responses, same `grants.jsonl` lines. That covers a Wakil
  pinned to hisn 0.4.3 and any revision-2 client. The 0.5.1 CLI sends
  nothing new to a session whose protocol revision is below 3.
- Nothing new blocks or slows an existing operation for a client without a
  seat credential.
- Journal records without seat fields (from 0.5.0) still parse, and
  `journal --seat` still matches them by label.
- `ls --json` gains only an additive `seats` key; `session.json` unknown
  fields still round-trip; `grants.jsonl` is unchanged in format.

## Known limitations

- **Decision A, first.** A seat is attribution and a guard against
  mistakes, not a security boundary: any same-uid process can omit the
  credential and be the owner. Real separation arrives with admission of
  other Unix users (the invites step).
- **Member exec can still signal.** A `member` may exec, and with the
  default no-signal-scope it can terminate other processes inside the
  sandbox — including the session's main command — even though `kill` is
  refused. The role table governs the control ops, not what a run command
  can do to its neighbours.
- **Seat names are visible to observers on disk.** `ls --json` lists seat
  names and roles for every session in a workspace without a credential.
  The observer-readable `sessioninfo` op deliberately omits them.
- **Expiry granularity.** An expiry is compared lexically against the
  current RFC 3339 UTC time; it is honoured on every authorization
  decision, but a running exec is not killed when a seat expires or is
  revoked mid-run (authorization is per request).
